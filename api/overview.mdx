The Cue API is a [Fastify 5](https://fastify.dev) REST API that powers every feature of the Cue personal planner. All request and response bodies are JSON. Every route is scoped to the authenticated caller's organisation — the org ID is derived from the JWT and never trusted from the request body, so a caller cannot read or write across tenant boundaries.

## Base URL

<Note>
  In **development**, the API runs on its own port separate from the Vite dev server. In **production**, the API serves the built web app from the same origin, so there is no CORS and the browser calls a relative `/api`.
</Note>

| Environment | Base URL |
|---|---|
| Development | `http://localhost:3002/api` |
| Production | Same origin as the web app — relative `/api` |

## Authentication

All routes require an `Authorization: Bearer <jwt>` header **except**:

- `GET /health` — server health check
- `POST /api/auth/register` — create an account
- `POST /api/auth/demo` — create a temporary demo account
- `POST /api/auth/login` — obtain a JWT
- `POST /api/auth/forgot` — request a password-reset link
- `POST /api/auth/reset` — spend a password-reset token
- `GET /api/oauth/:provider/callback` — OAuth redirect target

Obtain a token with `POST /api/auth/login`, then pass it in the `Authorization` header on every subsequent request. Tokens are signed with `JWT_SECRET` and expire after **30 days**. The user's role is read from the database on every request — not from the JWT — so removing access takes effect immediately rather than at token expiry.

## Error Response Shape

Every error from the API follows a consistent JSON envelope with a stable string `error` code that is safe to branch on in client code.

```json
{ "error": "<string_code>", "message": "<human readable>" }
```

### Common Error Codes

| HTTP Status | `error` code | Meaning |
|---|---|---|
| `400` | `invalid_input` | Request body failed schema validation (Zod error or bad UUID in URL) |
| `401` | `unauthorized` | Missing or invalid JWT |
| `403` | `wrong_password` | Delete-account or change-password request supplied the wrong current password |
| `404` | `not_found` | Resource does not exist or belongs to a different org |
| `409` | `email_taken` | Registration attempted with an address already in use |
| `409` | `time_conflict` | Commitment clashes with an existing slot |
| `415` | `unsupported_image_type` | Avatar upload sent an unsupported MIME type |
| `429` | `too_many_demos` | Demo account rate limit exceeded for this IP |
| `500` | `internal_error` | Unexpected server error — details are in the server log, not the response |

<Warning>
  A `500 internal_error` response intentionally omits database details. The full error is written to the server log. Surfacing raw Postgres messages to callers would expose the schema and aid attackers.
</Warning>

### Time Conflict Response

When saving or rescheduling a commitment produces a `409`, the response includes the clashing items so the caller can surface them to the user:

```json
{
  "error": "time_conflict",
  "conflicts": [
    {
      "id": "uuid",
      "title": "Team standup",
      "dueAt": "2025-10-14T09:00:00.000Z",
      "durationMinutes": 30
    }
  ]
}
```

## Health Endpoint

The health endpoint is intentionally outside the `/api` prefix and requires no authentication so load balancers and uptime monitors can reach it without a token.

```http
GET /health
```

```json
{ "ok": true, "push": true }
```

`push: true` means VAPID keys are configured and push notifications will be delivered. `push: false` means reminders will fire but no push will reach the device.

## Multi-Tenancy and Org Scoping

Every authenticated handler calls `scope(req)` from `src/auth.ts` to obtain the caller's `{ sub, orgId, email }` from the verified JWT. **Every database query filters on that `orgId`.** IDs supplied in the request body or URL are never used to determine which org's data is accessed — guessing a UUID cannot reach across tenant boundaries.

```ts
// Every handler looks like this — the orgId comes from the token, never the body.
const { sub, orgId } = scope(req)
const rows = await db.select().from(schema.commitments)
  .where(and(eq(schema.commitments.orgId, orgId), eq(schema.commitments.id, params.id)))
```

## Role-Based Access

Cue has two roles, set at the org level:

| Role | Who | What they can do |
|---|---|---|
| `owner` | The user who registered (created the org) | Everything, plus: change AI provider, store AI API key, manage billing |
| `member` | Invited teammates | All personal features; cannot touch org-level settings |

The role is read from the `users` row on every request. A role change takes effect on the very next API call — it is never cached in the token.

## Pagination

The API does not implement cursor or page-based pagination. Each list endpoint returns up to its configured internal limit. This is sufficient for a single-user or small-team planner; if you are building a heavily automated integration that needs to page through large datasets, consider querying the database directly.
