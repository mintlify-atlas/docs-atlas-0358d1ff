Running Cue on your own server gives you full control over your data, costs nothing beyond the server itself, and works on any Linux machine with a public IP. This guide walks through a complete production setup: PostgreSQL, a systemd service, and Caddy or nginx for TLS. Expect to spend about an hour the first time.

<Note>
  No third-party API key is required for the core features. Cue parses dates, recurrences, roles, and checklists with hand-written parsers — there is no account to open and nothing to bill for the basics.
</Note>

## Before you begin

<Warning>
  **Choose your OS carefully — Node 22 requires glibc 2.34 or newer.** This is a dynamic linker requirement, not a packaging problem that a different repository would solve.

  - ✅ Ubuntu 22.04+
  - ✅ Debian 12+
  - ✅ Amazon Linux 2023
  - ❌ Amazon Linux 2 — ships glibc 2.26, reached end of life 30 June 2026

  On Amazon Linux the login user is `ec2-user`, not `ubuntu`.
</Warning>

## Setup steps

<Steps>
  <Step title="Install Node 22+, PostgreSQL, and a reverse proxy">
    On Ubuntu or Debian, the quickest path uses NodeSource for Node and the system package manager for everything else:

    <Tabs>
      <Tab title="Ubuntu / Debian + Caddy">
        ```bash
        # Node 22
        curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
        sudo apt install -y nodejs

        # PostgreSQL
        sudo apt install -y postgresql

        # Caddy (handles TLS automatically — no certbot needed)
        sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
        curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
          | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
        curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
          | sudo tee /etc/apt/sources.list.d/caddy-stable.list
        sudo apt update && sudo apt install -y caddy
        ```
      </Tab>
      <Tab title="Ubuntu / Debian + nginx">
        ```bash
        # Node 22
        curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
        sudo apt install -y nodejs

        # PostgreSQL, nginx, and certbot
        sudo apt install -y postgresql nginx certbot python3-certbot-nginx
        ```
      </Tab>
      <Tab title="Amazon Linux 2023 + Caddy">
        ```bash
        # Node 22 (RPM repository — deb.nodesource.com is Debian-only)
        sudo dnf install -y tar
        curl -fsSL https://rpm.nodesource.com/setup_22.x | sudo bash -
        sudo dnf install -y nodejs

        # PostgreSQL
        sudo dnf install -y postgresql15-server
        sudo postgresql-setup --initdb
        sudo systemctl enable --now postgresql

        # Caddy (not in AL2023 repos — use the static binary)
        curl -fsSL "https://caddyserver.com/api/download?os=linux&arch=amd64" -o /tmp/caddy
        sudo install -m 755 /tmp/caddy /usr/local/bin/caddy
        sudo groupadd --system caddy
        sudo useradd --system --gid caddy --home-dir /var/lib/caddy \
          --create-home --shell /sbin/nologin caddy
        ```

        Create `/etc/systemd/system/caddy.service` with this content — the `AmbientCapabilities` line is what lets a non-root process bind ports 80 and 443:

        ```ini
        [Unit]
        Description=Caddy
        After=network.target

        [Service]
        User=caddy
        Group=caddy
        ExecStart=/usr/local/bin/caddy run --config /etc/caddy/Caddyfile
        ExecReload=/usr/local/bin/caddy reload --config /etc/caddy/Caddyfile --force
        Restart=on-failure
        AmbientCapabilities=CAP_NET_BIND_SERVICE

        [Install]
        WantedBy=multi-user.target
        ```

        ```bash
        sudo systemctl daemon-reload && sudo systemctl enable --now caddy
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Create the PostgreSQL role and database">
    ```bash
    sudo -u postgres psql \
      -c "create role cue login password 'pick-a-real-password'" \
      -c "create database cue owner cue"
    ```

    Replace `pick-a-real-password` with something generated by a password manager. You will paste it into `DATABASE_URL` in a later step.
  </Step>

  <Step title="Clone the repository and install dependencies">
    ```bash
    git clone <your-repo> /srv/cue
    cd /srv/cue
    npm ci --include=dev
    ```

    <Warning>
      **`--include=dev` is required here.** The build step needs Vite, which lives in devDependencies. A plain `npm ci` skips devDependencies and the build will fail.
    </Warning>
  </Step>

  <Step title="Generate VAPID keys for push notifications">
    ```bash
    npm run vapid
    ```

    This prints a VAPID public key and a VAPID private key. Copy both values — you will add them to `.env` in the next step. These keys are self-signed; there is no service to register with and nothing to pay.

    <Warning>
      Generate these once and keep the same pair. Changing either key later invalidates every existing browser push subscription, meaning all users must re-enable notifications.
    </Warning>
  </Step>

  <Step title="Write the .env file">
    Copy the example and fill in your values:

    ```bash
    cp .env.example .env
    ```

    Edit `/srv/cue/.env`. The minimum required values are:

    ```bash
    # ---- Required ----
    DATABASE_URL=postgres://cue:pick-a-real-password@localhost:5432/cue
    JWT_SECRET=<output of: openssl rand -hex 32>
    VAPID_PUBLIC_KEY=<from npm run vapid>
    VAPID_PRIVATE_KEY=<from npm run vapid>
    VAPID_SUBJECT=mailto:you@your-domain
    WEB_ORIGIN=https://your-domain.com
    PORT=3002

    # ---- Critical: must be blank in production ----
    # The API serves the built web app from the same origin.
    # Setting this sends every OAuth redirect back to localhost.
    VITE_API_URL=

    # ---- Security: loopback only, not reachable from outside ----
    HOST=127.0.0.1

    # ---- Required for AI and calendar OAuth token encryption ----
    ENCRYPTION_KEY=<output of: openssl rand -hex 32>
    ```

    Generate the two secrets with:

    ```bash
    openssl rand -hex 32   # for JWT_SECRET
    openssl rand -hex 32   # for ENCRYPTION_KEY
    ```

    Or with Node:

    ```bash
    node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
    ```

    <Note>
      **For managed databases (RDS, Neon, Supabase)**, append `?sslmode=require` to `DATABASE_URL`. Without it the driver connects unencrypted and RDS refuses with an error that says nothing about TLS:

      ```bash
      DATABASE_URL=postgres://cue:password@your-db.ap-south-1.rds.amazonaws.com:5432/cue?sslmode=require
      ```

      Use `require` rather than `verify-full` unless you have also installed the provider's CA bundle.
    </Note>

    The full list of optional variables (calendar integrations, SMTP, AI, place lookup) is documented in `.env.example` at the repo root. None of them are required for the core reminder and planning features.
  </Step>

  <Step title="Apply database migrations">
    ```bash
    CUE_NEW_DATABASE=1 npm run db:migrate
    ```

    <Warning>
      **`CUE_NEW_DATABASE=1` is for this first run only.** A brand-new database and one whose tables were deleted look identical to the migration runner. Without the flag, the runner refuses to proceed on a database with no migration history. Set it once now; every subsequent `db:migrate` (including the one in each deploy) leaves it off.
    </Warning>

    Migrations are forward-only and recorded in a `_migrations` table. Re-running `npm run db:migrate` on a database that is already up to date is always safe.
  </Step>

  <Step title="Build and do a smoke test">
    Build the web app and start the server:

    ```bash
    npm run build
    npm start
    ```

    In a second terminal, check the health endpoint:

    ```bash
    curl -s localhost:3002/health
    ```

    You should see:

    ```json
    {"ok":true,"push":true}
    ```

    If `push` is `false`, the VAPID keys were not picked up — re-check `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` in `.env`.

    Press `Ctrl+C` to stop the server once the check passes. The systemd service (step 9) will run it permanently.
  </Step>

  <Step title="Configure your reverse proxy">
    The app listens on `localhost:3002`. The proxy holds ports 80 and 443 and forwards everything to the app.

    <Tabs>
      <Tab title="Caddy">
        Caddy obtains and renews the TLS certificate automatically — no certbot, no cron job. Add a block to `/etc/caddy/Caddyfile`:

        ```
        your-domain.com {
            reverse_proxy 127.0.0.1:3002
        }
        ```

        Then reload:

        ```bash
        sudo systemctl reload caddy
        ```

        Caddy has no default request body limit, so the 5 MB voice-note uploads need no extra configuration. Make sure DNS is already resolving to your server before reloading — Caddy issues the certificate by answering a challenge on the domain name itself, and a name that does not resolve yet will fail and keep retrying with backoff.
      </Tab>
      <Tab title="nginx + certbot">
        First, obtain the certificate:

        ```bash
        sudo certbot --nginx -d your-domain.com
        ```

        certbot will edit your nginx config automatically. Add or confirm this `location` block in the server block it creates:

        ```nginx
        location / {
            proxy_pass         http://127.0.0.1:3002;
            proxy_set_header   Host              $host;
            proxy_set_header   X-Forwarded-Proto $scheme;
            client_max_body_size 6M;
        }
        ```

        <Warning>
          **`client_max_body_size 6M` is required.** Voice notes can reach 5 MB and nginx rejects larger bodies at its default 1 MB limit, returning a confusing 413 error. Set this to at least `6M`.
        </Warning>

        ```bash
        sudo nginx -t && sudo systemctl reload nginx
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Create the systemd service">
    Create `/etc/systemd/system/cue.service`:

    ```ini
    [Unit]
    Description=Cue personal planner
    After=network.target postgresql.service

    [Service]
    WorkingDirectory=/srv/cue
    ExecStart=/usr/bin/npm start -w @cue/api
    Restart=always
    User=cue
    EnvironmentFile=/srv/cue/.env

    [Install]
    WantedBy=multi-user.target
    ```

    <Note>
      `ExecStart` runs the API workspace only — `npm start -w @cue/api` starts the already-built API server. The web app was compiled into `apps/web/dist` during step 7 and is served from there. Never run `npm run build` from the service file; build once at deploy time.
    </Note>

    If you run the service as a dedicated `cue` user, create that user first:

    ```bash
    sudo useradd --system --home-dir /srv/cue --no-create-home cue
    sudo chown -R cue:cue /srv/cue
    ```

    Enable and start the service:

    ```bash
    sudo systemctl daemon-reload
    sudo systemctl enable --now cue
    ```

    Check it started cleanly:

    ```bash
    sudo systemctl status cue
    sudo journalctl -u cue -n 50
    ```
  </Step>

  <Step title="Install on your phone">
    Open the site in Chrome on Android and tap **Add to Home Screen**. On iPhone, use Safari → Share → **Add to Home Screen** (requires iOS 16.4+).

    <Warning>
      **On iPhone, this step is required before push notifications work at all.** Safari does not expose the Push API to a normal browser tab. The in-app install prompt explains which two taps to make.
    </Warning>
  </Step>
</Steps>

## Security

<CardGroup cols={2}>
  <Card title="Bind to loopback only" icon="network-wired">
    Set `HOST=127.0.0.1` in `.env`. The process is then not merely firewalled off — it is not listening on any interface that could carry a packet from outside. A mistakenly opened security-group rule cannot expose it.
  </Card>
  <Card title="What faces the internet" icon="globe">
    Only the proxy (port 443) faces the internet. The app process (port 3002) and PostgreSQL (port 5432) are loopback or VPC only. `/api/*` routes are reachable through the proxy and must be — they are behind authentication on every route.
  </Card>
</CardGroup>

### Reaching a private database from your laptop

Keep the database off the public internet. Tunnel through the app server instead:

```bash
ssh -i your-key.pem -N \
  -L 5432:your-db.ap-south-1.rds.amazonaws.com:5432 \
  ubuntu@your-server
```

Then point pgAdmin, DBeaver, `psql`, or `npm run db:studio` at `localhost:5432`. Use SSL mode **require**, not `verify-full`: through a tunnel the client thinks it is talking to `localhost` while the certificate says otherwise, so hostname verification fails even though the connection is perfectly encrypted.

## Updating

```bash
cd /srv/cue \
  && git pull \
  && npm ci --include=dev \
  && npm run db:migrate \
  && npm run build \
  && sudo systemctl restart cue
```

Migrations are forward-only and each file runs exactly once — re-running `db:migrate` on an up-to-date database is always safe. The `--include=dev` flag is required on every install because the build step needs Vite.
